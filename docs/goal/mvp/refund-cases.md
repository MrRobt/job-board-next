# 退款申请与权益冻结（阶段性实现）

## 已实现

- 已真实支付（PAID）的支付宝/微信工具次数包，用户可自行申请售后退款，填写 10～500 字说明；Mock、待支付、历史他人订单不可申请。
- 一笔有效申请使 ToolOrder.refundHold=true；余额计算与预留扣减都排除该订单的 ToolGrant，不影响免费试用或其他未冻结次数包。
- 申请为 ToolRefundCase(OPEN)，并非资金已退款。重复或并发申请使用条件 UPDATE，只允许一个成功；记录用户、订单、理由和申请时间。
- 管理员可以提交 10～500 字的审核依据驳回，记录审核人/时间，事务内解冻原订单；重复审核不得重复解冻。
- 用户端及后台均明确标明：冻结/驳回不代表渠道发生退款。不得通过修改 ToolOrder.status=REFUNDED 来假装实际返款。
- 新增 `prisma/migrations/20261117000300_refund_cases/migration.sql` 增量候选。**仅开发库 db push 成功**，生产部署迁移仍未验收。

## 尚未实现与不能假定

- 支付宝/微信真实退款申请、退款状态查询及验签、金额分摊或部分退款、资金对账，以及成功后撤回未消费权益。
- 对历史已经 RESERVED 的模型调用，提交退款申请不会撤销进行中的调用：需考虑等待运行结束、人工核账和消费者权益。
- 已使用次数、已有退款、服务质量和适用的消费者权益法规，必须由客服及法律/商户规则确认。不因用户已使用次数就自动拒绝依法享有的退款。
- 管理员当前只有「驳回并解冻」功能。不得自行标记 PROCESSING、SUCCEEDED 或 REFUNDED。
- 所有生产支付开关仍为 false，缺商户合法凭据和人工批准不得调用真实资金接口。

## 已获得测试证据

本轮 MySQL 集成测试 `refund request freezes only paid entitlements; review can reject with audit, without moving money`：跨用户访问、申请长度、并发申请、正确冻结余额、试用额度不受影响、普通用户不得审核、理由审计、拒绝并解冻、重复审核拒绝、Mock 拒绝、允许再次申请及数据库支付状态仍 PAID。

实际结果：8/8 单元，8/8 MySQL 集成，TypeScript 0 错误，Next.js 生产 build exit 0。

> 这是退款申请/权益冻结子闭环，不是退款资金闭环，也不是正式上线许可。
